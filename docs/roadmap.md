# Technical roadmap

Milestones are ordered by risk and independently verifiable. No milestone is runtime-accepted solely because source changes exist. This change implements only M1 after the Phase 0 audit.

| Milestone | Scope | Acceptance criteria |
| --- | --- | --- |
| M0 — Baseline audit | Architecture, findings, roadmap and contributor rules | Required four documents exist, confirmed findings link to source, missing functionality and blocked checks are explicit. Source audit delivered; execution baseline remains blocked by missing tooling. |
| M1 — Upload authorization (P0) | Require existing CandidateEditors on CV upload | Anonymous upload returns 401; all non-editor roles and roleless users return 403; HrSpecialist and combined roles reach file validation. Test through real MVC authorization with no external dependencies; run integration suite. Implementation/tests delivered in this change; execution pending SDK. |
| M2 — Upload consistency (P1) | Explicit unit of work, one PostgreSQL metadata/status commit, concurrency and storage compensation/reconciliation | PostgreSQL/MinIO Testcontainers tests cover successful upload, invalid status before storage, metadata/status rollback, duplicate requests, cancellation, storage failure, failed compensation, crash recovery and ambiguous commit outcomes. No claim of cross-resource atomicity. State/conflict responses deterministic; no lost status updates. |
| M3 — API error/validation boundary (P1) | ProblemDetails and central validation; uniqueness translation | Validation/not-found/conflict/unexpected errors share documented contracts; no internals leak. PostgreSQL email races produce 409. Frontend error parsing supports contract; handler and HTTP tests cover all mappings and cancellation. |
| M4 — PDF resource safety (P2) | Null-safe validation, bounded file/parser work, sanitized metadata | Tests for empty/null/spoofed/malformed/encrypted/oversized PDFs, long filenames, page/text limits and cancellation; existing valid extraction/upload scenarios still pass. |
| M5 — Deployment and operations baseline (P1/P2) | Environment secrets, production-safe configuration, readiness, migration policy, CI | Clean clone builds with documented SDK/Node versions; Compose config/build and smoke tests pass. Production fails safely on absent credentials/TLS config. CI runs backend tests, frontend lint/build/tests, container verification and dependency/security scanning. Readiness reports unavailable dependencies; migrations run under a documented controlled process. |
| M6 — Candidate frontend recovery (P2) | Existing-draft CV retry, editing, role-aware error/loading/empty states | Browser tests demonstrate create -> failed upload -> retry against same ID -> verify -> ready, plus update, filters and CV download; backend still rejects unauthorized callers. Responsive checks pass. |
| M7 — Hiring bounded context (Phase 2) | Clean Architecture, own PostgreSQL, creation and status transitions | HTTP + domain + integration tests prove authorized creation, candidate eligibility, legal/illegal transitions, durable persistence and deterministic conflicts. Publish API/schema and ADRs. |
| M8 — Reliable Candidate/Hiring messaging (Phase 2) | RabbitMQ/MassTransit, transactional Outbox, Inbox/idempotency, retry/fault handling | Real broker/database tests prove atomic business-write/outbox commit, restart/retry recovery, duplicate and out-of-order handling, eventual consistency, faults and dead-letter inspection/recovery. Document event versioning and reconciliation. |
| M9 — Hiring UI (Phase 3) | Request management/status views and role guards | E2E covers eligible candidate -> hiring request -> status changes with loading/empty/error states and backend authorization checks. |
| M10 — Observability and delivery (Phase 4) | Structured logs, correlation IDs, OpenTelemetry metrics/traces and deployment guidance | One demo workflow is traceable through HTTP and messaging; logs omit tokens/CV/PII; health and failure dashboards demonstrable; deployment/rollback tested and documented. |
| M11 — Portfolio presentation (Phase 5) | Accurate README, architecture/event explanations, ADRs, screenshots and demo | Fresh checkout follows setup successfully; every feature claim has a demonstrable test/demo. Document environment variables, security decisions, tests, limitations and trade-offs; label screenshot placeholders clearly. |

For each milestone report changed files, exact commands/results and remaining risks. Preserve current data models unless a reviewed migration is justified. Keep review changes scoped and do not automatically merge.
